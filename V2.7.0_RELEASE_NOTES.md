# Migration Failure Agent v2.7.0

## Adaptive Evidence Investigation

v2.7 changes the investigation workflow from a fixed evidence checklist into a bounded evidence-driven loop.

Flow:

Kafka/event -> classify -> required evidence -> evaluate uncertainty -> select approved next evidence -> collect -> evaluate -> diagnosis/action gate.

### Key behavior

- Initial required evidence remains deterministic and policy-controlled.
- Adaptive follow-up requests come only from `adaptive_investigation` rules in the active failure policy.
- The LLM is not permitted to invent capability IDs, raw SPL, SQL, kubectl, shell commands, or infrastructure operations.
- Every evidence round is bounded by a policy-defined `max_rounds`.
- Capability results retain explicit `SUCCESS`, `NO_DATA`, `UNKNOWN`, `UNAVAILABLE`, and `ERROR` states.
- Diagnosis is not considered sufficient merely because the initial checklist is complete.
- Recovery gates require diagnostic sufficiency before allowing a retry decision.
- If targeted evidence is unavailable, the agent fails closed with `INSUFFICIENT_EVIDENCE` or `BLOCKED`.

### Storage CSI timeout example

Initial evidence:

- PVC pending
- CSI provisioning timeout
- storage backend healthy
- migration failed

Adaptive evidence requests:

1. CSI controller/provisioner errors
2. PVC provisioning events
3. CSI provisioning latency

When those signals are available, the agent can produce a stronger CSI provisioning-path diagnosis. When they are unavailable, it stops rather than guessing.
